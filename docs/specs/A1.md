# A1 · Sign in with LinkedIn

**Status:** Draft, waiting for approval (Razam Sir + Arman Hussain). Two points need a written decision first (section "Decisions needed").

## User story
As a LinkedIn user, I click "Continue with LinkedIn", approve on LinkedIn's own page, and land in Qiva Reach with my name and photo already filled in. No password, and nothing is ever posted for me.

## Acceptance criteria (locked)
LinkedIn OpenID Connect login works; name, photo and headline saved; no password or session cookie stored; token encrypted at rest.

## What LinkedIn gives us (checked in LinkedIn's documentation, 14 Oct 2026)
"Sign In with LinkedIn using OpenID Connect" returns only: `sub` (an id), `name`, `given_name`, `family_name`, `picture`, `locale`, and optionally `email` and `email_verified`. **It does not return the headline.** The access token lives 60 days. Refresh tokens are only for a small set of LinkedIn partners, so there is none. Asking for a different permission later (for example posting, `w_member_social`) invalidates tokens issued before, so Phase 2 will ask for it in a separate, explicit step.

## How it works
- Supabase's LinkedIn (OIDC) provider handles the login (`signInWithOAuth` with provider `linkedin_oidc`, redirect URL `https://toxnipocsujizbdcexdr.supabase.co/auth/v1/callback`), including the CSRF check. Our existing `/auth/callback` finishes the sign-in.
- Supabase does not keep LinkedIn's token. Our server reads it once, right after sign-in, in `/auth/callback`, and saves it encrypted (below). It never goes to the browser.
- An existing email account with the same verified email is joined automatically by Supabase. Otherwise a new account is made. Manual linking must be switched on in Supabase (Sign In / Providers).

## Data
- `linkedin_profiles` (exists): `linkedin_sub` (unique), `name`, `headline`, `picture_url`, `access_token_enc`, `token_expires_at`. `refresh_token_enc` stays empty (LinkedIn gives none). The token columns are already hidden from the browser by column permissions.
- `profiles.full_name` and `profiles.avatar_url` are filled from LinkedIn on every LinkedIn sign-in, so they stay current. LinkedIn photo links can expire, so the app shows initials when the photo fails to load. We do not download or copy the photo.
- `token_expires_at` = sign-in time + 60 days (LinkedIn's fixed lifetime).
- **Encryption:** AES-256-GCM in `src/lib/crypto.ts`, key in the environment variable `TOKEN_ENCRYPTION_KEY` (32 random bytes, set locally and in Vercel, never in code or chat). Stored as `v1:<iv>:<tag>:<ciphertext>`; the `v1` prefix allows key rotation. The decrypt function exists only for server code. The token is never logged or returned from any route.
- `audit_log` gets an entry for `linkedin_connected` and `linkedin_removed` (user id only, no token).

## Compliance and privacy
- LinkedIn gate: official OpenID Connect sign-in, started by a human click, minimal permissions, no scraping, no stored LinkedIn password or cookie. We would show this to LinkedIn's developer-partnership team.
- The privacy policy must list the LinkedIn data we keep (name, photo link, email, encrypted access token) and why (Arman, with Q-004).
- Phase 1 stores the token but nothing reads it yet. It is kept because the criterion requires it and Phase 2 builds on it; Phase 2 will replace it with a token that also allows posting.

- PostHog events: `signed_up` and `signed_in` with method `linkedin`, `linkedin_connected`, `linkedin_removed`.
- Signing in again with LinkedIn refreshes name, photo and the stored token.

## Acceptance tests
Automatic:
1. Unit: encrypt and decrypt round trip; a different key fails; a changed byte fails; two encryptions of the same text differ; the stored text never contains the token; unknown version prefix is rejected.
2. Unit: the callback saves name, photo, `linkedin_sub`, encrypted token and expiry from a fake session; a missing email is handled; a `linkedin_sub` already on another user returns the "already connected" message.
3. Database: a signed-in browser user cannot read `access_token_enc` or `refresh_token_enc` (permission error), and cannot write `linkedin_profiles`; another user cannot read this user's row.
4. Browser: the LinkedIn button is on /sign-in and, when clicked, reaches `linkedin.com/oauth/v2/authorization` with scope `openid profile email`, the Supabase callback as `redirect_uri` and a `state` value (we stop there; we do not type credentials).
5. Browser: `/auth/callback` with a cancel or error from LinkedIn shows the right message; Settings shows "Connect LinkedIn" for an email user and starts the link flow.
6. Browser: with a seeded encrypted token, the token text never appears in any page or network response; "Remove LinkedIn access" deletes the row and clears the token (LinkedIn revocation is stubbed in tests).
7. 390 px phone, keyboard only, visible focus on the new button and settings section.

By hand, with real LinkedIn accounts (Razam Sir and Arman; LinkedIn blocks automated logins):
8. New LinkedIn user: lands on /onboarding; name and photo are saved; the stored token starts with `v1:` and contains no readable token.
9. Email account first, then LinkedIn with the same verified email: one account, not two.
10. Cancel on LinkedIn's page; second Qiva Reach account using the same LinkedIn account is blocked with the message.
11. After sign-in, our cookies are only Supabase's; no LinkedIn password or session cookie is stored.
12. Hakscan run clean on auth routes.
